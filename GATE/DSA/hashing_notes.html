00 — OVERVIEW

The Big Picture of Hashing

How every concept connects — from the naive solution to the complete system.

The core story: We need to store and retrieve data instantly (O(1)). Arrays give O(1) — but only if we use the key directly as an index. That only works when keys are small, integer, and dense. Hashing is the art of making any key behave like such an index — by compressing it into a small integer — while carefully managing the inevitable collisions.

When to Use Hashing

Choose hashing when order doesn't matter and relationship between keys doesn't matter. If you need ordering, a BST is better. If insertion order matters, use a queue/stack.

🔑 Key Insight Worst-case hashing is O(n) — just like a linked list. But we don't use hashing for worst case. The worst case (all keys colliding into one slot) essentially never happens in practice, just like the worst case of Randomised QuickSort choosing the worst pivot every time.

Real-World Uses

Compilers

Is int a keyword or a variable name? Hash table lookup in O(1).

File Systems

Human path C:/users/desktop → sector number via hash.

Python dict

Every Python dictionary is a hash table. 40–60% of Python programs use one.

01 — FOUNDATIONS

Direct Address Table

The simplest possible hashing — just an array. Understanding its limitations is what motivates everything else.

Problem to solve: Store data for bus services numbered 0–999. We need O(1) insert, delete, and search. Idea: Use the bus number directly as the array index.

How It Works

A Direct Address Table is just an array where the key itself is the index. No computation needed.

# a[] is the table (array of size max_key)
def insert(key, data):
    a[key] = data        # O(1) — direct index

def delete(key):
    a[key] = None       # O(1) — just nullify

def find(key):
    return a[key]        # O(1) — direct access

Bus number 2? → a[2]. Bus number 998? → a[998]. Instantly. No searching, no looping.

Why It Breaks — 3 Limitations

  • Keys must be non-negative integers

    What if your key is "Sachin" or "151A"? You cannot use a string as an array index directly. You first have to convert it to an integer (called pre-hashing). This is solvable but annoying.

  • Range of keys must be small

    Suppose keys are phone numbers (10 digits → 10⁹ possibilities). To store just 100 phone numbers, your array needs 1,000,000,000 slots. That is billions of wasted memory locations. IPv4 addresses? 2³² = 4 billion slots for maybe 100 active connections.

    ❌ DAT for phone numbers

    Array size: 1,000,000,000
    Actual items: 100
    Waste: 99.999990%

    ✅ Hash table instead

    Array size: ~130
    Actual items: 100
    Load: ~77%

  • Keys must be dense (continuous, few gaps)

    If keys are 1, 500, 10000, your array needs 10001 slots but uses only 3. The memory for indices 2–499 and 501–9999 is wasted. A hash table compresses these sparse keys into a compact space.

    • 💡 The Bridge to Hashing Hashing overcomes these limits with two ideas: (1) convert non-integer keys to integers first (pre-hashing), then (2) compress large integers into a small range using a hash function. The hash function is the core innovation.
    02 — HASH FUNCTIONS

    Hash Functions

    The core of hashing: deterministically map any key to a small index. Small choices here have big consequences.

    Formal Setup

    Universe of Keys (U)

    All possible keys. E.g. all 10-digit phone numbers = 10⁹ possibilities. Usually huge.

    Actual Keys (K)

    Keys you'll actually use. E.g. only 100 phone numbers. We never know K exactly — we approximate.

    Hash Table (T)

    Array with m slots (0 to m−1). The hash function maps every key to one of these m slots.

    h : U → {0, 1, ..., m−1}
    The hash function maps any key from the universe to one slot in the table

    We map from U (not K) because the hash function must handle any future key generically, not just today's known keys.

    The Division Method (Most Common)

    h(k) = k % m
    Map key k into a table of m slots

    Example: Table size m = 997

    66,752,378 % 997 = 237  |  68,744,483 % 997 = 336

    Hash Function Explorer
    Enter a key and table size above.

    How to Choose m (Table Size) — Critical!

    The choice of m dramatically affects how well the hash function distributes keys.

    ❌ Bad Choice: m = 2ⁿ (power of two)

    Why power of 2 is bad

    When m = 2ⁿ, computing k mod m is identical to extracting only the last n bits of k in binary.

    Example: k = 1011000111011010 (binary), m = 2⁶

    k mod 2⁶ = last 6 bits = 011010 (ignores the first 10 bits!)

    Two keys that differ only in high bits will have the same hash. The hash function sees only a fraction of the key — violating property #1 (must depend on every bit).

    33 mod 4 = 33 mod 2² = take last 2 bits of 33 = 01 = 1

    57 mod 4 = take last 2 bits of 57 = 01 = 1 (different key, same hash!)

    ❌ Bad Choice: m = 10ⁿ

    Hash = last n decimal digits of k. Keys 973 and 1293 both hash to 3 if m=10. Same problem — only partial key used.

    ✅ Good Choice: Prime number close to a power of two

    🧠 Why Prime Works A prime number shares no common factor with any key. This ensures the hash function doesn't "favor" certain slots due to shared divisibility patterns. For example, m=997 (prime near 2¹⁰=1024) works far better than m=1024 for most key distributions.

    3 Properties Every Good Hash Function Must Have

  • Depends on every bit of k

    The hash should change if any bit of the key changes. A function that only looks at the last 3 bits will map 8 different high-value keys to the same slot.

    ❌ Bad
    h(k) = lowest 3 bits of k
    h(1010010100010) = 2
    h(0001001000010) = 2 ← collision!
    ✅ Better
    h(k) = sum of all bits of k
    h(1010010100010) = 6
    Different keys → different sums
  • Spreads values uniformly across all m buckets

    No bucket should be "favored." All m slots should receive approximately the same number of keys.

    ❌ Bad (m=263 table)
    h(k) = k mod 2
    → only values 0 or 1
    → 261 slots never used!
    ✅ Better
    h(k) = k mod 263
    → values 0..262
    → all slots can receive keys
  • Efficient to compute — O(1)

    The whole point of hashing is speed. If computing h(k) itself takes O(n) time, we've gained nothing. The hash function must be a simple, fast computation — like a mod operation.

    ❌ Bad
    h(k) = solution to PDE
    *$^% with parameter k
    → computationally expensive
    ✅ Good
    h(k) = k mod 263
    → single division operation
    → truly O(1)

    • Simple Uniform Hashing — The Ideal

    Definition
    Any given key is equally likely to hash into any of the m slots, independently of where any other key hashed.
    Pr[h(x) = i] = 1/m    for ALL keys x and ALL slot indices i
    Each of the m slots has probability 1/m of receiving any given key. This is the theoretical assumption used in all our average-case analysis. In practice, universal hashing (a variant like (a·k + b) mod p mod m) provably achieves this.
    03 — THE CORE PROBLEM

    Collisions

    Two different keys mapping to the same slot. Not a bug — a mathematical certainty.

    The unavoidable reality: Since |U| (all possible keys) is always much larger than m (table size), by the Pigeonhole Principle, there must always exist two different keys that hash to the same slot. A well-designed hash function minimizes collisions but can never eliminate them. We need a resolution strategy.

    Since |U| > m  →  at least two keys share the same hash value
    Pigeonhole Principle: m pigeons into fewer holes ⟹ some hole has ≥ 2

    Two Resolution Families

    ⚠️ Terminology Confusion — Know This! These terms are used inconsistently across textbooks. Here's the cheat sheet:
    Common NameAlso CalledCore Idea
    Separate ChainingOpen Hashing, Closed AddressingColliding keys stored in external linked lists
    Open AddressingClosed HashingColliding keys stored inside the table — probe for another slot

    We will use: Separate Chaining and Open Addressing — these are the clearest names.

    04 — RESOLUTION STRATEGY 1

    Separate Chaining

    Let every slot hold a linked list. Multiple keys at the same slot → they form a chain. Simple, flexible, robust.

    Core idea: When two keys map to the same slot, don't panic — just append to a linked list at that slot. The slot holds the head of the list. Each new collision = new node in the list. The list can grow arbitrarily — no table size constraint on n.

    Visualized Example

    Insert 10, 22, 107, 12, 42 with h(k) = k mod 10

    Code: Insert, Search, Delete

    # Hash table using chaining — each slot is a list
table = [[] for _ in range(m)]   # m slots, each is a list

def insert(key, value):
    slot = key % m                  # compute hash → O(1)
    for k, v in table[slot]:        # check key doesn't exist
        if k == key: return           # already present, skip
    table[slot].append((key, value)) # add to chain → O(1) amortized

def search(key):
    slot = key % m
    for k, v in table[slot]:        # traverse chain at this slot
        if k == key: return v
    return None                       # not found

def delete(key):
    slot = key % m
    table[slot] = [(k,v) for k,v in table[slot] if k != key]

    Interactive Chaining Demo

    Separate Chaining Visualizer

    Load Factor α — The Key Metric

    α = n / m    (n = items stored, m = table slots)
    In chaining: α is the AVERAGE number of items per chain. Can be > 1.

    If n=1000 items and m=100 slots, then α=10 — each chain has on average 10 items. The load factor directly controls performance.

    05 — AVERAGE CASE ANALYSIS

    Chaining Analysis

    How fast is chaining on average? The theorems and proofs — including the ingenious "go back in time" trick.

    ⚠️ Important Clarification — Are Keys Unique? Yes — all n keys in the hash table are distinct (unique). There are no duplicates. When we say "n items in the table", n is the count of unique keys. Insert always checks if key exists first (unsuccessful search) before adding.
    📌 Assumption All analysis uses Simple Uniform Hashing: every key is equally likely (prob 1/m) to land in any slot, independently of other keys.

    Theorem 11.1 — Unsuccessful Search

    Theorem 11.1 (CLRS)
    In a hash table using chaining, an unsuccessful search takes average-case time Θ(1 + α), assuming simple uniform hashing.

    Intuition (Why 1 + α?)

  • Go to slot h(k)

    Computing h(k) = k % m takes O(1). This is the "1" in "1 + α".

  • Traverse the entire chain

    Unsuccessful search means the key is NOT there. You must go all the way to the end of the chain to confirm this. You cannot stop early. Average chain length = α. So you traverse α nodes.

  • Total: 1 (compute hash) + α (traverse chain) = 1 + α

    When is this O(1)? Only when α is a constant. α = n/m. If we ensure m = Θ(n) (table size proportional to items), then α = constant, and search is O(1).

    • If m = Θ(n) → α = n/m = constant → Unsuccessful search = O(1)

    Theorem 11.2 — Successful Search

    Theorem 11.2 (CLRS)
    In a hash table using chaining, a successful search takes average-case time Θ(1 + α) (specifically 1 + α/2), assuming simple uniform hashing.

    The Brilliant "Go Back in Time" Logical Trick

    🎩 The Key Insight (Almost Magic) The cost of successfully searching for item i (when the table has n items) is the same as the cost of unsuccessfully searching for item i when it was first inserted (when the table had only i−1 items). Why? Because inserting follows exactly the same steps: search first (unsuccessfully), then add.

    Full Proof — Successful Search in Chaining

    Goal: Find the average time to successfully search for the i-th item, given n total items in the table.

    We claim these three situations take identical time:

    (A) Successfully search for item i, with n items in table

    (B) ≡ Insert item i, with i−1 items in table (you follow the same path)

    (C) ≡ Unsuccessfully search for item i, with i−1 items in table

    Why (B) ≡ (C)? To insert item i, you first check it's not already present — that IS an unsuccessful search. So the insert cost = unsuccessful search cost.

    Cost of unsuccessful search with i−1 items:

    = 1 + (i−1)/m     (1 for hash computation + chain of avg length (i-1)/m)

    Average over all n items (for i = 1 to n):

    Average successful search time

    = (1/n) · Σᵢ₌₁ⁿ [1 + (i−1)/m]

    = 1 + (1/n) · (1/m) · Σᵢ₌₀ⁿ⁻¹ i

    = 1 + (1/nm) · [n(n−1)/2]

    = 1 + (n−1)/(2m)

    ≈ 1 + α/2       (since α = n/m)

    = Θ(1 + α) ✓

    Conclusion: If m = Θ(n) → α = constant → successful search = O(1).

    Summary Table

    OperationAverage CaseIf m=Θ(n)Worst Case
    Search (unsuccessful)Θ(1 + α)O(1)O(n)
    Search (successful)Θ(1 + α)O(1)O(n)
    InsertΘ(1 + α)O(1)O(n)
    DeleteΘ(1 + α)O(1)O(n)
    ✅ Did Chaining Achieve the Goal? Yes, if we maintain m = Θ(n). By keeping the number of slots proportional to the number of items, α stays constant, and all operations are O(1) average. Chaining is reliable and works even when α > 1 (you can keep inserting even when the table is "full").
    06 — RESOLUTION STRATEGY 2

    Open Addressing

    No external chains. Every key lives inside the table. When a slot is taken, systematically hunt for a free one — called probing.

    Fundamental constraint: Since all n items must fit in m slots, we always need n ≤ m → α ≤ 1 always. The table can "fill up" completely, after which no insertions are possible. This is the key tradeoff vs chaining.

    Probe function: h : U × {0,1,...,m−1} → {0,1,...,m−1}
    Takes (key, probe_number) → slot. Probe sequence must be a permutation of all m slots.

    The probe sequence for key k is ⟨h(k,0), h(k,1), ..., h(k,m−1)⟩ — a permutation of {0,...,m-1}. This guarantees that if a slot exists, we'll eventually find it.

    General probing formula:

    h(k, i) = (h′(k) + f(i)) mod m
    Different choices of f(i) → different probing strategies

    6a — Linear Probing

    f(i) = i   →   h(k, i) = (h′(k) + i) mod m
    Try h′(k), then h′(k)+1, then h′(k)+2, ... wrapping around

    Step-by-step: Insert 76, 93, 40, 47, 10, 55 (m=7, h=k%7)

    Interactive Linear Probing

    Open Addressing — Probing Visualizer

    Code: Insert, Search, Delete (with Tombstones!)

    EMPTY = None
TOMBSTONE = "DELETED"   # marker for deleted slots
table = [EMPTY] * m

def _hash(key, i):
    return (key % m + i) % m     # linear probing

def insert(key):
    for i in range(m):
        slot = _hash(key, i)
        if table[slot] in (EMPTY, TOMBSTONE):
            table[slot] = key       # found a free slot → insert
            return
    raise Exception("Table full")

def search(key):
    for i in range(m):
        slot = _hash(key, i)
        if table[slot] == EMPTY:   # TRUE empty → stop, not found
            return False
        if table[slot] == key:     # found it
            return True
        # if TOMBSTONE → keep going! (crucial difference)
    return False

def delete(key):
    for i in range(m):
        slot = _hash(key, i)
        if table[slot] == EMPTY: return   # not found
        if table[slot] == key:
            table[slot] = TOMBSTONE      # ← MUST use tombstone, not None!
            return

    Why Tombstones? — The Deletion Problem

    ⚠️ Critical: Why You Cannot Just Set Slot to None on Delete

    Suppose 76 is at slot 6. We insert 55 (also hashes to 6) → it gets placed at slot 1 (after probing past slot 6). Now we delete 76 and set slot 6 to None. Later we search for 55: we hash to slot 6, find None, conclude "not found" — but 55 IS in slot 1!

    The None breaks the probe chain. Tombstone = "I was deleted but keep probing past me".

    Primary Clustering — Linear Probing's Problem

    ⚠️ Primary Clustering When h(k₁) = h(k₂) = h(k₃) = h(k₄), all four items probe the same sequence: same start, same next slots. They pile up in a consecutive cluster. Each new insertion landing near this cluster makes it longer. This is called a primary cluster. As clusters grow, performance degrades even for keys that don't originally hash there.

    6b — Quadratic Probing

    f(i) = i²   →   h(k, i) = (h′(k) + c₁i + c₂i²) mod m    (c₂ ≠ 0)
    Probe jumps grow quadratically: try h′(k), h′(k)+1, h′(k)+4, h′(k)+9, ...

    Solves: Primary Clustering

    Keys at the same slot no longer probe consecutive locations. The quadratic jumps scatter them across the table.

    ⚠️ Important — Always Use h′(k) as the Base If key k hashes to slot 5, the probe sequence is: 5+0², 5+1², 5+2², 5+3², ... Always from the original h′(k)=5. NEVER do 5+1²=6, then 6+2²=10. The formula is always (h′(k) + i²) mod m.

    Creates: Secondary Clustering

    ⚠️ Secondary Clustering If h(k₁) = h(k₂) = 1, both follow the identical probe sequence: 1, 2, 5, 10, ... (1+0², 1+1², 1+4²). Different keys, same starting slot → same entire path. This is secondary clustering — invisible clusters based on probe path, not physical adjacency.

    Why? In quadratic probing, f(i) = i² depends only on i, not on k. So if two keys start at the same slot (h(k₁,0) = h(k₂,0)), they will visit the exact same slots for all i.

    Cycles in Quadratic Probing

    The probe sequence may revisit slots, potentially missing empty ones that exist. However, this is not a real problem — with careful choices of c₁, c₂, and h′(k), cycles are eliminated. The guarantee can always be achieved.

    6c — Double Hashing

    h(k, i) = (h₁(k) + i · h₂(k)) mod m
    h₁ gives the initial slot. h₂ gives the step size — and it depends on the key!

    Probe sequence: h₁(k), h₁(k)+h₂(k), h₁(k)+2h₂(k), ...

    Classic choice (CLRS): h₁(k) = k mod m and h₂(k) = 1 + (k mod m′) where m′ is slightly less than m.

    Solves: Secondary Clustering

    ✅ How Double Hashing Eliminates Secondary Clusters If h₁(k₁) = h₁(k₂) (same initial slot) BUT h₂(k₁) ≠ h₂(k₂), the step sizes differ → completely different probe paths!

    Linear probing: same start → same path
    Quadratic probing: same start → same path (f(i) doesn't use k)
    Double hashing: same start + different step → DIFFERENT paths ✓ 
    def _hash(key, i, m):
    m_prime = m - 1               # choose prime slightly < m
    h1 = key % m
    h2 = 1 + (key % m_prime)      # step size — key-dependent!
    return (h1 + i * h2) % m

    6d — Probe Sequence Comparison: m vs m² vs m!

    The number of distinct probe sequences a method can generate tells us how close it gets to the ideal of uniform hashing.

    Counting Distinct Probe Sequences Per Key

    Linear Probing:

    Probe sequence: h(k), h(k)+1, h(k)+2, ..., h(k)+m−1    (all mod m)

    h(k) can be 0, 1, ..., m−1 → m choices → m distinct sequences

    Once h(k) is fixed, all subsequent slots are determined. No further freedom.

    Quadratic Probing: Same analysis. h(k) determines everything → m sequences.

    Double Hashing:

    h(k,i) = h₁(k) + i·h₂(k)    (mod m)

    h₁(k): m possible values. h₂(k): m possible values.

    Together: m × m = m² (start, step) pairs → m² distinct sequences

    Once h₁ and h₂ fixed, subsequent slots are determined — no further freedom.

    Uniform Hashing (ideal):

    Any permutation of {0,...,m-1} is a valid probe sequence.

    Total permutations = m!    (e.g. m=10 → 3,628,800 sequences)

    MethodSequences/KeyHow Close to Ideal?Cluster Problem
    Linear ProbingmVery far from m!Primary clusters
    Quadratic ProbingmVery far from m!Secondary clusters
    Double Hashingm²Much closer to m!Neither (in practice)
    Uniform Hashingm!The ideal (theoretical)None
    📚 Source (CLRS / MIT 6.006 / Stanford CS161) "Uniform hashing assumes each key's probe sequence is equally likely to be any of the m! permutations of {0,...,m-1}. Neither linear nor double hashing necessarily satisfies this criterion, but in practice, they often almost satisfy it for real-world input distributions." Double hashing with m² possible sequences is the best practical approximation of uniform hashing.
    07 — OPEN ADDRESSING ANALYSIS

    Open Addressing Analysis

    How many probes does open addressing need on average? The geometric series derivation — and a beautiful reusable template.

    📌 Assumption Analysis is with respect to Uniform Hashing — not specifically linear or quadratic or double hashing. Any of the m! permutations is equally likely as a probe sequence. And since n ≤ m, α = n/m ≤ 1.

    Theorem 11.6 — Unsuccessful Search

    Theorem 11.6 (CLRS)
    Given an open-address hash table with load factor α = n/m < 1, the expected number of probes in an unsuccessful search is at most 1/(1−α), assuming uniform hashing.

    Building the Intuition

    Unsuccessful search = keep probing until we hit a true empty slot.

    • P(hitting a filled slot) = n/m = α (filled/total)
    • P(hitting an empty slot) = 1 − α = (m−n)/m
    • We probe repeatedly until we hit empty. This is like: "how many coin tosses until heads, where P(heads) = 1−α?"
    🎯 Reusable Template (Works in Hashing, CN, Probability, everywhere) If the probability of success = p, then the expected number of attempts to get success = 1/p.

    Here: P(empty slot) = 1−α → E[probes] = 1/(1−α).

    Full Derivation (Geometric Series Method)

    Proof — Expected probes for unsuccessful search

    Build a chart of (attempts, probability):

    Attempt 1: hit empty immediately → prob = (1−α)

    Attempt 2: hit filled, then empty → prob = α·(1−α)

    Attempt 3: hit filled twice, then empty → prob = α²·(1−α)

    Attempt k: prob = α^(k−1)·(1−α)

    Expected number of attempts:

    E[X] = Σₖ₌₁^∞ k · α^(k−1) · (1−α)

    = (1−α) · Σₖ₌₁^∞ k · α^(k−1)

    We need: S = Σₖ₌₁^∞ k · αᵏ⁻¹ = 1 + 2α + 3α² + 4α³ + ...

    AGP trick to find S:

    S = 1 + 2α + 3α² + 4α³ + ...

    α·S = α + 2α² + 3α³ + ...

    S − αS = 1 + α + α² + α³ + ... = 1/(1−α)    (geometric series)

    S(1−α) = 1/(1−α)

    S = 1/(1−α)²

    Therefore:

    E[X] = (1−α) · S = (1−α) · 1/(1−α)² = 1/(1−α) ✓

    Practical meaning at various load factors:

    2
    probes at α=0.5
    (50% full)
    5
    probes at α=0.8
    (80% full)
    10
    probes at α=0.9
    (90% full)
    ∞
    probes at α=1
    (100% full)

    Theorem 11.7 — Successful Search

    Theorem 11.7 (CLRS)
    Expected probes in a successful search ≤ (1/α) · ln(1/(1−α)), assuming uniform hashing.

    Derivation — Successful Search

    Same "go back in time" trick as chaining:

    Successfully search for item i (with n items) ≡ Insert item i (when there were i−1 items)

    ≡ Unsuccessfully search for item i with i−1 items in table

    Cost of unsuccessful search with i−1 items: = 1/(1 − (i−1)/m) = m/(m−i+1)

    Average over all n items:

    (1/n) · Σᵢ₌₁ⁿ m/(m−i+1)

    = (m/n) · Σₖ₌ₘ₋ₙ₊₁ᵐ 1/k     (change of variable)

    ≤ (1/α) · ∫ₘ₋ₙᵐ (1/x)dx     (integral approximation)

    = (1/α) · [ln(m) − ln(m−n)]

    = (1/α) · ln(m/(m−n))

    = (1/α) · ln(1/(1−α)) ✓

    Final Comparison Table

    MethodUnsuccessful SearchSuccessful Search
    ChainingΘ(1 + α)Θ(1 + α)
    Open Addressing (uniform)O(1/(1−α))O((1/α)·ln(1/(1−α)))
    📊 Key Graph Insight As α → 1 (table nearly full), open addressing performance explodes toward infinity (1/(1−α) → ∞). Chaining degrades gracefully (1+α grows linearly). This is why chaining is preferred when you don't control the load factor, and why open addressing tables are typically kept below α=0.7–0.75.
    08 — PROBABILITY IN HASHING

    Bernoulli Random Variable in Hashing

    The simplest probabilistic model — and the building block for all our hashing expectations.

    Why probability here? We want to calculate things like "how many items end up in slot 1?" or "how many collisions happen?" These are random outcomes. Bernoulli and Binomial RVs give us precise tools to answer them.

    What is a Bernoulli RV? (In Hashing Terms)

    A Bernoulli RV takes exactly two values: 1 (success) or 0 (failure).

    In hashing: Let Xᵢ = 1 if item i maps to slot 1, else Xᵢ = 0.

    • By uniform hashing: P(item maps to slot 1) = 1/m
    • So: P(Xᵢ = 1) = 1/m, P(Xᵢ = 0) = 1 − 1/m
    E[Xᵢ] = 1·(1/m) + 0·(1 − 1/m) = 1/m
    Var[Xᵢ] = p(1−p) = (1/m)·(1 − 1/m)

    Where p = 1/m is the probability of success (item mapping to the target slot).

    🔑 Why Bernoulli is Perfect Here Each item either goes to slot 1 or it doesn't. Binary outcome. Independent across items (by uniform hashing assumption). This is exactly the Bernoulli scenario. The genius: instead of computing complex joint probabilities, we define one simple Bernoulli RV per item, then sum them using linearity of expectation.

    Binomial Random Variable in Hashing

    A Binomial RV = sum of n independent Bernoulli RVs. It counts total successes in n trials.

    In hashing: X = total items in slot 1 = X₁ + X₂ + ... + Xₙ (each Xᵢ is Bernoulli with p=1/m)

    P(X = k) = C(n,k) · pᵏ · (1−p)^(n−k)
    k successes in n independent Bernoulli trials

    Key Stats (derived from indicator RVs):

    # X = X₁ + X₂ + ... + Xₙ    (n independent Bernoulli RVs, each p=1/m)

# Expected value — uses LINEARITY OF EXPECTATION (no independence needed!)
E[X] = E[X₁] + E[X₂] + ... + E[Xₙ] = n · (1/m) = n/m

# Variance — REQUIRES independence (which we have here)
Var[X] = n · p · (1−p) = n/m · (1 − 1/m)
    🧠 Linearity of Expectation — The Most Useful Trick E[X₁ + X₂ + ... + Xₙ] = E[X₁] + E[X₂] + ... + E[Xₙ] — always, even if X₁, X₂, ... are not independent. This is why we break complex hashing questions into simple Bernoulli indicator RVs and just sum expectations.

    Binomial Example: Party Problem

    30 people each accept an invitation independently with probability 1/3. X = number who accept.

    Hashing lens: 30 "items" each randomly assigned to "accept" (slot) or "reject" (not in slot), with p=1/3. This is Binomial(n=30, p=1/3).

    # Binomial(n=30, p=1/3)
E[X]   = n·p        = 30 · 1/3 = 10
Var[X] = n·p·(1−p) = 30 · 1/3 · 2/3 = 20/3
E[X²]  = Var[X] + (E[X])² = 20/3 + 100 = 320/3
E[X² − 4X + 5] = 320/3 − 4·10 + 5 = 215/3   # by linearity

    Dice Example

    Fair die rolled 72,000 times. X₃ = times die shows 3. Think: 72,000 items hashed into 6 slots uniformly. Binomial(n=72000, p=1/6).

    E[X₃]   = 72000 · 1/6 = 12000
Var[X₃] = 72000 · 1/6 · 5/6 = 10000

    09 — APPLYING PROBABILITY TO HASHING

    3 Classic Hashing Questions

    Expected items per slot, expected empty slots, expected collisions. All solved with indicator Bernoulli RVs.

    Setup: n items, m slots, uniform hashing (every item goes to each slot with probability 1/m). All items are distinct. We use indicator RVs: Xᵢ = 1 if [something], else 0. Then E[Xᵢ] = P(event). Then sum via linearity.

    Q1: Expected Items Per Slot

    How many items do we expect to find in any given slot (say, slot 1)?

    Derivation

    Let X = total items in slot 1. Define indicator Xᵢ = 1 if item i lands in slot 1, else 0.

    X = X₁ + X₂ + ... + Xₙ

    P(Xᵢ = 1) = 1/m    (uniform hashing: any item equally likely to be in any slot)

    E[Xᵢ] = 1/m

    E[X] = E[X₁] + ... + E[Xₙ] = n · (1/m) = n/m = α

    ✅ Hashing Meaning The load factor α = n/m IS the expected number of items per slot. This mathematically confirms our intuitive definition of α as "average chain length" in chaining. Not just an approximation — it's exact under uniform hashing.

    Q2: Expected Number of Empty Slots

    After inserting n items into m slots, how many slots remain empty on average?

    Derivation

    Let Y = total empty slots. Define indicator Yᵢ = 1 if slot i is empty, else 0.

    Y = Y₁ + Y₂ + ... + Yₘ

    P(slot i is empty after n insertions) = P(all n items avoided slot i):

    P(one item misses slot i) = (m−1)/m = 1 − 1/m

    P(all n items miss slot i) = (1 − 1/m)ⁿ

    E[Y] = m · (1 − 1/m)ⁿ

    🧠 Surprising Result When n = m (table "full" by count): E[Y] = m·(1 − 1/m)^m ≈ m/e ≈ 0.368m. Even when you've inserted as many items as there are slots, ~37% of slots are still empty! This explains why rehashing at α=0.7 is common — performance degrades fast beyond that, while many slots sit empty.

    Q3: Expected Number of Collisions

    In n insertions, how many collisions will happen on average?

    Derivation

    Let Z = total collisions. Define indicator Zᵢ = 1 if the i-th insertion causes a collision.

    Z = Z₁ + Z₂ + ... + Zₙ

    P(collision at i-th insertion) = P(item i lands in one of the i−1 already-filled slots):

    P(Z₁ = 1) = 0                  (table empty, can't collide)

    P(Z₂ = 1) = 1/m               (1 filled slot out of m)

    P(Z₃ = 1) = 2/m               (2 filled slots out of m)

    P(Zᵢ = 1) = (i−1)/m           (i−1 filled slots out of m)

    E[Z] = 0 + 1/m + 2/m + ... + (n−1)/m

    = (1/m) · [0 + 1 + 2 + ... + (n−1)]

    = (1/m) · n(n−1)/2

    = n(n−1) / (2m)

    ✅ Hashing Meaning With n=1000 items and m=997 slots: E[Z] = 1000·999/(2·997) ≈ 500. About 500 collisions in 1000 insertions! This confirms collisions are frequent and unavoidable — which is exactly why we need robust collision resolution strategies (chaining or open addressing).
    🎯 The Complete Picture Every formula we've derived connects back to the load factor α:
    • Expected items/slot = α  |  Expected empty slots = m·(1−1/m)ⁿ  |  Expected collisions = n(n−1)/(2m)
    • Chaining search time = Θ(1+α)  |  OA search time = O(1/(1−α))
    α is the single most important number in hash table performance. Keep it small (via m=Θ(n)) for O(1) everything.

    Core Rules
    Constraint
    All n items stored inside the table. α ≤ 1 always. Table can become 100% full.
    Probe Sequence
    ⟨h(k,0), h(k,1), …, h(k,m−1)⟩ must be a permutation of {0…m−1}. Guarantees finding empty if one exists.
    General Formula
    h(k,i) = (h′(k) + f(i)) % m
    Choice of f(i) → LP / QP / DH
    6a · Linear Probing
    f(i) = i
    h(k,i) = (k%m + i) % m

    Try h′(k), then h′(k)+1, h′(k)+2 … wrapping around.

    ✅ Simple, great cache locality
    ❌ Primary Clustering: consecutive filled block grows → blocks unrelated keys that hash nearby
    m distinct probe sequences per key
    ❌ Deletion needs TOMBSTONE (cannot just set NULL)
    6b · Quadratic Probing
    f(i) = i²
    h(k,i) = (h′(k) + i²) % m

    Jumps: +0, +1, +4, +9, +16… always from original h′(k).

    ✅ Eliminates primary clustering
    ❌ Secondary Clustering: same h′(k) → f(i) unchanged → entire probe path identical for both keys
    ❌ Cycle trap: non-prime m can cause the sequence to miss slots. Always use prime m.
    m distinct sequences · must use prime m
    6c · Double Hashing
    h(k,i) = (h₁(k) + i·h₂(k)) % m
    h₁ = k % m
    h₂ = 1 + (k % m′)  where m′ < m
    ✅ Eliminates both primary & secondary clustering
    ✅ m² distinct probe sequences (h₁, h₂ pair)
    ⚠️ h₂ must never = 0. The "1 +" guarantees this. If h₂=0, the probe loops on the same slot forever.

    Same h₁ + different h₂ → completely different paths after probe 0.

    More sequences → closer to theoretical uniform hashing → fewer expected collisions per probe.

    Tombstone — Why Deletion is Hard in OA

    In OA you cannot set a deleted slot to NULL/None.

    NULL delete → broken
    Probe chain breaks. Search hits NULL early and reports "not found" even though the key exists further along.
    TOMB → correct
    TOMB = "deleted, keep probing past me."
    NULL = "never used, stop here."
    Invariant: Key K reachable from h(K) without crossing any NULL. TOMB preserves this; NULL breaks it.

    Open Addressing Analysis

    Theorem 11.6 · Unsuccessful Search (OA)
    ≤ 1 / (1 − α)

    Assumes uniform hashing, α < 1.

    Derivation — Geometric Series:
    P(hit empty) = 1−α. Keep probing until empty.
    Reusable template: P(success) = p → E[attempts] = 1/p
    ∴ E[probes] = 1/(1−α)
    Full proof: E[X] = (1−α)·S where S = Σk·αᵏ⁻¹. AGP trick: S − αS = 1/(1−α) → S = 1/(1−α)². So E[X] = (1−α)/(1−α)² = 1/(1−α).

    Theorem 11.7 · Successful Search (OA)
    ≤ (1/α) · ln(1 / (1−α))
    Derivation: "Go back in time" → cost searching for item i ≡ unsuccessful search with i−1 items = 1/(1−(i−1)/m) = m/(m−i+1).
    Average over all n: (1/n)·Σ m/(m−i+1) = (1/α)·∫ dx/x → (1/α)·ln(1/(1−α)).
    MethodUnsuccessfulSuccessful
    ChainingΘ(1 + α)Θ(1 + α/2)
    OA (uniform)1/(1−α)(1/α)·ln(1/(1−α))
    Key contrast: As α→1, OA time→∞. Chaining stays Θ(1+α). Keep OA table at α ≤ 0.7–0.75.

    Probability in Hashing

    Bernoulli Random Variable

    Binary outcome: X ∈ {0, 1}.  P(X = 1) = p.

    E[X] = p
    Var[X] = p(1 − p)

    In hashing: Xᵢ = 1 if item i goes to target slot, else 0. Since uniform hashing: p = 1/m.

    Indicator RV technique: define one Bernoulli per item/event → sum → use linearity of expectation.
    Binomial RV — B(n, p)

    Sum of n independent Bernoulli(p) RVs. Counts total successes in n trials.

    P(X=k) = C(n,k)·pᵏ·(1−p)ⁿ⁻ᵏ
    E[X] = np
    Var[X] = np(1−p)
    E[X²] = Var[X] + (E[X])²
    Linearity of Expectation:
    E[X₁+…+Xₙ] = ΣE[Xᵢ] — always, even without independence.
    3 Classic Hashing Questions
    Q1: E[items in a slot]
    = n/m = α
    Load factor IS the expected chain length.
    Q2: E[empty slots]
    = m · (1 − 1/m)ⁿ
    When n=m: ≈ m/e ≈ 37% still empty even when "full".
    Q3: E[collisions]
    = n(n−1) / (2m)
    P(i-th insert collides) = (i−1)/m. Sum i=1…n.

    Common Traps & Pitfalls
    OA deletion: Never set slot to NULL. Use TOMBSTONE — it means "deleted, keep probing."
    QP base slot: Always probe from original h′(k), NOT from the previous probe slot.
    QP + non-prime m: Quadratic probing can cycle and miss empty slots. Must use prime m.
    DH h₂ = 0: Leads to infinite loop on the same slot. The "1 +" in h₂ = 1 + (k%m′) prevents this.
    m = 2ⁿ or 10ⁿ: Only partial key bits used → collision clusters → avoid.
    Naming: "Open Addressing" ≠ "Open Hashing." They are opposite strategies.
    Secondary clustering: Caused when f(i) doesn't depend on k (LP and QP). DH fixes this because h₂ is key-dependent.
    Worst case = O(n) for all methods. Hashing is analyzed on average case only.
    "Go back in time" trick is used in both Thm 11.2 (chaining) and Thm 11.7 (OA): successful search for item i ≡ unsuccessful search when item i was inserted.
    1/(1−α) template: Whenever P(success) = p in a repeated trial, E[attempts until success] = 1/p. Reuse everywhere.
