Section 01

Why Analyze Algorithms?

Before writing complex code, understand why measuring performance matters — and why the naive approaches fail.

The Central Question

"Will my program handle large, real-world input?"

Two problems hide here: Time (why is it slow?) and Space (why does it run out of memory?). A face-detector app that is too slow or an app eating 500 MB will be rejected by users.

Three Approaches — Evolution of Thinking

Approach 1 — Manual Clock Timing (Not Practical) You run the program with a stopwatch. Simple, but the result depends entirely on the hardware. Sachin on MacBook Pro: 100ms. Deepak on HP: 1000ms — which algorithm is truly faster? You simply cannot tell!
Approach 2 — A Posteriori Analysis (Platform Dependent) Run the algorithm, measure actual time. The result is platform-dependent: different CPU clock speeds, instruction sets, memory access times all change the number. This is not practical for comparing algorithms fairly.
Approach 3 — A Priori Analysis → Step Count → Asymptotic Analysis ✅ Count the number of basic operations (steps) the algorithm performs — not actual time. This is hardware-independent. Then simplify the step count using asymptotic analysis to focus only on what grows fast. This is what we use!

What Is Input Size?

Every algorithm takes input. The complexity is always a function of input size.

Insert in Linked List (size n)

Input: Linked list of n nodes + value to insert

Input size ≈ n

T(n) — function of n

Multiply Two Numbers

First number has n digits, second has m digits

Input size = n + m

T(m, n) — function of both

Graph Algorithm (Bipartite check)

Graph G with V vertices (n) and E edges (m)

Input size = n + m

T(m, n) — function of both

💡
Key Insight (Knuth, 1970s) Use the scientific method to understand performance. Count operations, not clock time. This gives a mathematical characterization that is platform-independent.
Section 02

Step Count Method

Count each operation. Every assignment, comparison, arithmetic operation = 1 step.

Example 1 — Sum of Array

Algorithm Sum(a, n)          // Step Count (T.C.)    Space Count
{
  sum = 0;               // 1                    1 word (sum)
  for i = 1 to n do      // n+1                  1 word (i, n)
    sum = sum + a[i];    // n                    n words (array a[])
  return sum;            // 1
}
                         // Total: 2n+3          (n+3) words

Time Complexity: 2n + 3

Space Complexity: (n+3) words

Example 2 — Matrix Addition

Algorithm Add(a, b, c, m, n)
{
  for i = 1 to m do         // m+1 times
    for j = 1 to n do       // m(n+1) times
      c[i,j] = a[i,j] + b[i,j]; // m·n times
}
                              // Total = 2mn + 2m + 2

Problem with Exact Step Count

⚠️
Why Bother With Exact Counts? If an algorithm has 1000 lines, calculating exact step counts for each line is impractical. We need a simpler bound. Can we approximate 3n + 2 as just n? Yes! This leads us to Asymptotic Analysis.
Section 03

Asymptotic Analysis

The magical simplification — focus only on what matters as input grows large.

The Core Idea — Rounding for Functions

Asymptotic Analysis = "Rounding" for functions.

Just like 1,000,001 ≈ 1,000,000 in everyday math:

→ 3n² ≈ n² in asymptotic sense

→ n² + n → significant term is n²

Why? Because for large n, the dominant term overwhelms all others. At n=1,000,000, the n² term is a million times larger than n.

What Asymptotic Analysis Does

✂️ Drops Constants

3n² → n²

The constant 3 doesn't affect growth rate.

✂️ Drops Lower-Order Terms

n² + n + 5 → n²

For large n, n² dominates completely.

📊 Captures Growth Rate

If n doubles (n → 2n): n² grows by ×4, n³ by ×8. The rate of growth is what matters.

🎯 For Large Input

Asymptotic analysis is designed for large input sizes. For small inputs, any algorithm is fast — nobody cares.

The 5 Asymptotic Notations

These are mathematical notations (not CS-specific) used to express relationships between functions:

O
Big-O Notation
T(n) ≤ c·g(n) for all n ≥ n₀ (∃ c, n₀ > 0)
Upper bound — "at most this much"
Ω
Big-Omega Notation
T(n) ≥ c·g(n) for all n ≥ n₀ (∃ c, n₀ > 0)
Lower bound — "at least this much"
Θ
Theta Notation
c₁·g(n) ≤ T(n) ≤ c₂·g(n) for all n ≥ n₀
Tight bound — "exactly this order" (both O and Ω)
o
Little-o Notation
T(n) < c·g(n) for ALL c > 0 (∃ n₀ > 0)
Strict upper bound — "strictly less than"
ω
Little-omega Notation
T(n) > c·g(n) for ALL c > 0 (∃ n₀ > 0)
Strict lower bound — "strictly greater than"
✨
Abuse of Notation (Important!) When we write f(n) = O(g(n)), the "=" is NOT equality! It means f(n) ∈ O(g(n)) — f belongs to the SET of all functions bounded by g. O(n²) is a set containing n², 3n²+5, n, log n, 1, etc. We write "=" for convenience, but never misuse it.
Section 04

Big-O Notation — Upper Bound

The most popular notation. Tells you the worst your algorithm will ever do.

Formal Definition

DEFINITION
T(n) = O(g(n)) ⟺ ∃ c > 0, n₀ ≥ 0 such that ∀ n ≥ n₀: T(n) ≤ c·g(n)

Visual Intuition

Plain English Meaning

T(n) = O(n²) means:

"For any input of size n, my algorithm takes AT MOST c·n² steps." (for some constant c, after some turning point n₀)

→ Your manager asks: "How long will it take?" You say: "Never more than n² operations, guaranteed."

The Turning Point (n₀) Concept

Before n₀, anything can happen — f(n) might be bigger or smaller than c·g(n). We don't care about small input!

After n₀, c·g(n) is always ≥ f(n). This is what asymptotic analysis cares about — behavior for large n.

Examples with c and n₀

Note: You will rarely need to find c and n₀ in practice. But understanding them builds intuition.

Example 1 Easy

Prove: 3n + 2 = O(n)

We need: 3n + 2 ≤ c·n for some c and n₀.

Try c = 4: 3n + 2 ≤ 4n ⟺ 2 ≤ n So for n₀ = 3: 3(3)+2=11, 4(3)=12 ✓ ∴ c=4, n₀=3 works. Also c=10000, n₀=1 works. Many answers valid!
Example 2 Easy

Prove: 1 + n + n² = O(n²)

Since 1 ≤ n², n ≤ n² for n ≥ 1: 1 + n + n² ≤ n² + n² + n² = 3n² ∴ c=3, n₀=2 works → 1+n+n² = O(n²)

Also true: 1+n+n² = O(n³), O(n⁴), O(2ⁿ)... All are valid upper bounds!

Example 3 Medium

Is 2²ⁿ = O(2ⁿ)?

Need: 2²ⁿ ≤ c·2ⁿ ⟺ 2ⁿ ≤ c But c is a constant! 2ⁿ grows unboundedly. No constant c can ever bound 2ⁿ from above. ∴ 2²ⁿ ≠ O(2ⁿ) — FALSE!
Example 4 Medium

Is 2ⁿ⁺¹ = O(2ⁿ)?

2ⁿ⁺¹ = 2 · 2ⁿ Need: 2·2ⁿ ≤ c·2ⁿ ⟺ 2 ≤ c ∴ c=3, n₀=1 works → 2ⁿ⁺¹ = O(2ⁿ) — TRUE ✓

Key Rules for Big-O

Rule 1: Drop Lower Terms

n² + n + 1 = O(n²)

Rule 2: Drop Constants

5n = O(n)

Rule 3: Can Go Higher

n² = O(n³) = O(n⁴) = ... All valid, just not tight.

Rule 4: Cannot Go Lower

n² ≠ O(n) (n cannot upper-bound n²)

Section 05

Big-Ω Notation — Lower Bound

The mirror of Big-O. Tells you the minimum your algorithm will ever take.

Formal Definition

DEFINITION
T(n) = Ω(g(n)) ⟺ ∃ c > 0, n₀ ≥ 0 such that ∀ n ≥ n₀: T(n) ≥ c·g(n)

Visual Intuition

Relationship with Big-O

KEY THEOREM
T(n) = O(g(n)) ⟺ g(n) = Ω(T(n)) (f ≤ g means g ≥ f — they're transpose of each other)

T(n) = Ω(n²) means:

"For any input of size n, my algorithm takes AT LEAST c·n² steps."

→ "Whatever input you give me, I'm guaranteed to take at least n² operations."

Important Observation

Big-O (Upper)

You can always go HIGHER: if T(n) = O(n²), then also O(n³), O(n⁴)...

Big-Ω (Lower)

You can always go LOWER: if T(n) = Ω(n²), then also Ω(n), Ω(log n), Ω(1)...

Trivial Bounds (Always True for Any Algorithm)

For any algorithm:

  • T(n) = Ω(1) — at least constant time (always)
  • T(n) = O(∞) — at most infinite time (trivially true)

These are the "trivial" bounds — mathematically correct but useless!

Donald Knuth invented Theta notation because students gave trivial bounds in their answers.

Examples Easy
  • 3n + 2 = Ω(n) — c=1, n₀=1: 3n+2 ≥ n ✓
  • 10n² + 4n + 2 = Ω(n²) — c=1, n₀=1 ✓
  • n² = Ω(n), also Ω(log n), also Ω(1)
Section 06

Theta (Θ) Notation — Tight Bound

The most precise and honest bound. Says exactly what order of growth your function has.

Formal Definition

DEFINITION
T(n) = Θ(g(n)) ⟺ T(n) = O(g(n)) AND T(n) = Ω(g(n)) ⟺ ∃ c₁, c₂ > 0, n₀ such that ∀ n ≥ n₀: c₁·g(n) ≤ T(n) ≤ c₂·g(n)

Visual Intuition

Plain English Meaning

T(n) = Θ(n²) means:

"The algorithm takes exactly n² order of steps. Not more, not less. The functions are asymptotically equal."

→ 3n² = Θ(n²) (constants don't matter, growth rate matters)

→ 3n² ≠ Θ(n³) (n³ is fundamentally different growth)

The "Maggi Noodles" Analogy

How long to cook Maggi?

  • O(1 day) — At most 1 day. True but useless (too loose).
  • Ω(10 seconds) — At least 10 sec. True but useless (too loose).
  • Θ(3 minutes) — Exactly ~3 minutes. Precise and useful!

Theta gives you the tightest, most honest answer.

Implication Chain

LOGIC
If T(n) = Θ(g(n)) → T(n) = O(g(n)) AND T(n) = Ω(g(n)) If T(n) = O(g(n)) AND T(n) = Ω(g(n)) → T(n) = Θ(g(n)) Big-O alone does NOT imply Theta. Big-Ω alone does NOT imply Theta.

Important: Algorithm Cases vs Notations

⚠️
COMMON MISCONCEPTION — DO NOT DO THIS! People wrongly think: Best case = Ω, Worst case = O, Average case = Θ. This is FALSE. You can use ANY notation with ANY case. Worst-case can be Θ. Best-case can be O. Average can be Ω. They are independent concepts!
❌ WRONG
  • Best case → Ω
  • Worst case → O
  • Average case → Θ
✅ CORRECT
  • Best case can be Θ(1)
  • Worst case can be Θ(n²)
  • We can say: for every input, algorithm takes Θ(n²)
Examples Easy
  • 3n² = Θ(n²) — 2n² ≤ 3n² ≤ 4n², c₁=2, c₂=4 ✓
  • 10n² + 4n + 2 = Θ(n²) — significant term is n²
  • 6·2ⁿ + n² = Θ(2ⁿ) — c₁=1, c₂=7, works for n≥5 ✓
  • 3n + 10¹⁰ = Θ(n) — even HUGE constants become irrelevant at large n!

Comparing O, Ω, Θ Side by Side

Section 07

Little-o and Little-ω Notations

Strict bounds — when the difference is a function, not just a constant.

Little-o (Strict Upper Bound)

DEFINITION
T(n) = o(g(n)) ⟺ ∀ c > 0, ∃ n₀ > 0 such that ∀ n ≥ n₀: T(n) < c·g(n) KEY DIFFERENCE from Big-O: Big-O: "there EXISTS one c that works" Little-o: "it works for ALL c (however small)"
Big-O (n² = O(2n²))

Find ONE c that works.

c=1 works: n² ≤ 2n² ✓

But c=1/10: n² ≤ 2n²/10? Only if n²≤n²/5. NO!

→ Only needs one c → Big-O ✓

Little-o (n² ≠ o(2n²))

Must work for ALL c.

c=1/10: n² < 2n²/10? n² < n²/5? FALSE!

Not true for all c → NOT little-o

→ Need ALL c to work → fails

When is f(n) = o(g(n))? When the difference is a function (not just a constant).

  • n² = o(n³) ✓ — difference is a factor of n (function)
  • n² ≠ o(2n²) ✗ — difference is factor of 2 (constant)
  • n² = O(2n²) ✓ — big-O is fine with constant factors

Little-ω (Strict Lower Bound)

DEFINITION
T(n) = ω(g(n)) ⟺ ∀ c > 0, ∃ n₀ > 0 such that ∀ n ≥ n₀: T(n) > c·g(n) T(n) = ω(g(n)) ⟺ g(n) = o(T(n)) [transpose property]

Incomparability

Some Functions Cannot Be Compared!

n^(1+sin n) vs n

Since sin(n) oscillates between -1 and 1, the exponent oscillates between 0 and 2. Sometimes n^(1+sin n) = n⁰ = 1, sometimes = n². No stable turning point exists!

→ These functions are incomparable — none of O, Ω, Θ applies.

n! vs nⁿ — Stirling's Approximation

Stirling's Approximation

n! ≈ √(2πn) · (n/e)ⁿ
  • Before log: n! < nⁿ (strictly) → n! = o(nⁿ)
  • After log: log(n!) = Θ(n log n) — EXACTLY equal!
  • Proof: log(n!) = log(n·(n-1)·...·1) = Σlog(i) from i=1 to n
  • Upper bound: all n terms ≤ log n → log(n!) ≤ n log n
  • Lower bound: take n/2 terms (each ≥ log(n/2)) → log(n!) ≥ (n/2)log(n/2) = Θ(n log n)
  • Therefore: log(n!) = Θ(n log n)
Section 09

Function Comparison — The Toolbox

How to compare two functions asymptotically. These tools always work.

Tool 1: Cancel Common Terms

If both functions share a common factor, divide both by it first.

Compare n² and n³ → divide by n² → compare 1 and n → n³ is bigger ✓

Compare n²·log n and n·log²n → divide by n·log n → compare n and log n → first is bigger ✓

Tool 2: When to Ignore Constants

Only safe to ignore constants in these forms:

  • c · f(n) → safe to ignore c (e.g., 3n² → n²)
  • f(n) + d → safe to ignore d (e.g., n² + 5 → n²)

NEVER ignore constants when they are "inside" the function:

  • n^(5+n) — the 5 is part of exponent! n^5 is huge.
  • 2^(2n) — the 2 inside doubles the exponent!
  • (5/2)^n vs 2^n — the 5/2 base matters!

Tool 3: Take Logarithm

Why log works: Log is order-preserving: a > b ⟹ log a > log b (always true for real numbers).

What log does: It compresses huge gaps. Before log: n and 2ⁿ are vastly far apart. After log: log n and n are still far apart → you can conclude 2ⁿ > n.

When it fails: After log, if you get equal functions, you cannot conclude anything about the original. (e.g., n² vs n³: after log → 2 log n vs 3 log n → both are Θ(log n) → CAN'T CONCLUDE)

log(f) > log(g) ⟹ f > g asymptotically ✓ log(f) < log(g) ⟹ f < g asymptotically ✓ log(f) = log(g) ⟹ CANNOT SAY anything about f vs g ✗

Tool 4: Assume a Form of n

Substitute n = 2^k or n = 2^(2^k) to simplify complex expressions involving nested logs/powers.

Example: Compare (log n)^(log log n) vs (log log n)^(log n)

Let n = 2^k → log n = k, log log n = log k

Now compare k^(log k) vs (log k)^k → take log → (log k)² vs k·log(log k) → k dominates → second is larger

Key Relationships to Remember

Polynomial vs Log

n^ε > (log n)^k for any ε>0, any k>0

Even the tiniest polynomial power beats any log power!

Exponential vs Polynomial

a^n > n^k for any a>1, any k>0

Any exponential beats any polynomial!

Log Base Changes

log₂n = Θ(log₁₀n) — all log bases differ only by a constant factor!

log_a(n) = log_b(n) / log_b(a)

Exponential Base Matters

2^n ≠ Θ(3^n) — different exponential bases are asymptotically different!

3^n / 2^n = (3/2)^n → ∞

Log Properties Reference

LOG RULES
a = b^(log_b a) // basic log_c(ab) = log_c a + log_c b // product log_b(a^n) = n·log_b a // power log_b a = log_c a / log_c b // change base log_b(1/a) = -log_b a // reciprocal log_b a = 1 / log_a b // inversion a^(log_b c) = c^(log_b a) // swap base/argument log_b a > log_b b iff a > b (b>1) // order preserving

Worked Examples

Compare n^(log₂ n) vs 2^n Medium

Take log₂ both sides:

log(n^(log₂n)) = (log₂n)² = (log n)² log(2ⁿ) = n Compare: (log n)² vs n By n^ε > (log n)^k rule: n > (log n)² ✓ ∴ 2ⁿ > n^(log n) asymptotically → n^(log n) = O(2ⁿ)
Compare n^(log₂ n) vs n^(log₁₀ n) Hard

Which exponent is bigger? log₂n vs log₁₀n

log₂n = log₁₀n / log₁₀2 ≈ log₁₀n / 0.3 ∴ log₂n > log₁₀n (since dividing by fraction < 1 makes it bigger) Higher exponent means larger function: ∴ n^(log₂ n) > n^(log₁₀ n) → n^(log₁₀ n) = O(n^(log₂ n))
Arrange: 2^(log n), (log n)^2, √(log n), log(log n) Hard

Let k = log n (substituting):

A = 2^k, B = k², C = √k, D = log k Order: D < C < B < A (by polynomial/exponential rules) log(log n) < √(log n) < (log n)² < 2^(log n) ∴ log log n < √log n < (log n)² < 2^(log n)
Arrange: 2^(2^n), n!, 4^n, 2^n Hard
After log: log(2^(2^n)) = 2^n, log(n!) ≈ n log n, log(4^n) = n log 4, log(2^n) = n Order of log values: n < n log 4 < n log n < 2^n ∴ 2^n < 4^n < n! < 2^(2^n)

Properties of Asymptotic Notations

PropertyStatementWhy
Transitivity f=O(g), g=O(h) → f=O(h)
(same for Ω, Θ, o, ω)		 If f≤g and g≤h, then f≤h
Reflexivity f=O(f), f=Ω(f), f=Θ(f) f=f trivially satisfies all bounds
Symmetry f=Θ(g) ⟺ g=Θ(f) Equality is symmetric (only Theta!)
Transpose Sym. f=O(g) ⟺ g=Ω(f)
f=o(g) ⟺ g=ω(f)		 Less-than swaps with greater-than
Implication f=Θ(g) → f=O(g) AND f=Ω(g) Equal implies both upper and lower
Combination f=O(g) AND f=Ω(g) → f=Θ(g) Upper+lower together = tight bound

Best Case, Worst Case, Average Case

Best Case

The input that causes the minimum number of operations.

Example (search in linked list): Searching for the first element → O(1)

Worst Case

The input that causes the maximum number of operations.

Example: Searching for the last element → O(n)

Average Case

Expected operations over all possible inputs (probabilistic).

Much harder to compute. Involves expectation theory.

Section 11

Loop Complexity Analysis

Systematic method to determine time complexity from code structure.

Pattern 1 — Increment by Constant

RULE
for(i=1; i≤n; i+=a) → runs ⌈n/a⌉ times → O(n/a) = O(n) for(i=n; i≥1; i-=a) → same: O(n/a) = O(n) [reverse is same!]
Examples Easy
for(i=1; i<=n; i++)    // O(n)   — increment by 1
for(i=1; i<=n; i+=2)   // O(n/2) = O(n) — increment by 2
for(i=1; i<=n; i+=5)   // O(n/5) = O(n) — increment by 5
for(i=n; i>=1; i--)    // O(n)   — decrement by 1

Pattern 2 — Multiply/Divide by Constant

RULE
for(i=1; i≤n; i*=k) → runs log_k(n) times → O(log n) for(i=n; i≥1; i/=k) → same: O(log n)
Why? Derivation Medium

i starts at 1, then 2, then 4, ..., after k steps = 2^k. Stops when 2^k = n → k = log₂n.

for(i=1; i<=n; i*=2)   // O(log₂n)
for(i=1; i<=n; i*=3)   // O(log₃n)
for(i=n; i>=1; i/=2)   // O(log₂n)  — reverse is same!
for(i=2; i<=2^n; i*=2) // log₂(2^n) = n  → O(n)
for(i=0; i<n; i*=2)    // INFINITE LOOP! 0*2=0 always!

Pattern 3 — Squaring (i = i²)

RULE
for(i=2; i≤n; i=i*i) → runs O(log log n) times
Why? Derivation Hard

i starts at 2 = 2^1, then 4 = 2^2, then 16 = 2^4, then 2^8... After k steps: i = 2^(2^k).

Stops when 2^(2^k) = n → 2^k = log₂n → k = log₂(log₂n)

for(i=2; i<=n; i=i*i)             // O(log log n)
for(i=n; i>=2; i=sqrt(i))         // O(log log n)  — square root = reverse
for(i=2; i<=n*n; i=i*i)           // O(log log n²) = O(log(2 log n)) = O(log log n)

Nested Loops

// Independent nested loops
for(i=0; i<n; i++)           // n times
  for(j=0; j<n; j++)         // n times
    stmt;                     → O(n²)

// Dependent inner loop
for(i=0; i<n; i++)           // n times
  for(j=i; j<n; j++)         // (n-i) times
    stmt;                     → Sum: n+(n-1)+...+1 = n(n+1)/2 = O(n²)

// Inner loop depends on i, increments by i
for(i=0; i<n; i++)           // n times
  for(j=1; j<n; j+=i)        // n/i times
    stmt;                     → Σ(n/i) for i=1 to n = n·H(n) ≈ n·ln(n) = O(n log n)

Type 1 — Finding c and n₀

Q: Find c,n₀ for 3n+2 = O(n) Easy
Need: 3n+2 ≤ c·n Try c=4: 3n+2 ≤ 4n ↔ 2 ≤ n → true for n₀=3 Answer: c=4, n₀=3 (many answers valid: c=10000,n₀=1; etc.)
Q: Is 2n² = O(n³)? Easy
Need: 2n² ≤ c·n³ ↔ 2 ≤ c·n c=1, n₀=2: 2(4)=8, 1·8=8 ✓ YES: c=1, n₀=2 works → 2n² = O(n³)

Type 3 — Comparison Ordering

Q: Arrange in increasing order: n!, 4ⁿ, 2ⁿ, 2^(2^n) Hard
2^n: log = n 4^n = (2^2)^n = 2^(2n): log = 2n n!: log = n log n (by Stirling) 2^(2^n): log = 2^n Compare logs: n < 2n < n log n < 2^n Order: 2ⁿ < 4ⁿ < n! < 2^(2^n)
Q: f(n)=n^log₂(n), g(n)=2ⁿ — which is bigger? Hard
log f = (log₂n)² log g = n Compare: (log n)² vs n n^ε beats (log n)^k for any ε,k → n > (log n)² 2ⁿ > n^(log n) → f(n) = O(g(n)) → B is answer
Q: f(n)=2ⁿ, g(n)=n^√n — which is bigger? Tricky
log f = n · log 2 = n (constant) log g = √n · log n Compare: n vs √n · log n → divide by √n √n vs log n → n^(1/2) > log n (polynomial > log) log f > log g → f > g → 2ⁿ > n^√n → f=Ω(g)

Type 4 — Gate-Style MCQ

Q: f(n)=n, g(n)=n² — which is true? Easy

n < n² for large n → f is smaller → f(n) = O(g(n)) ✓

Q: f(n)=n², g(n)=2ⁿ — which is true? Easy

n² < 2ⁿ for large n → f(n) = O(g(n)) ✓ and more precisely f(n) = o(g(n))

Q: n^(5+n) vs n^n — can we ignore the 5? Tricky
n^(5+n) = n^5 · n^n n^(5+n) / n^n = n^5 → ∞ The 5 CANNOT be ignored — it represents n^5 factor! n^(5+n) is STRICTLY LARGER than n^n → n^n = o(n^(5+n))

⚡ Quick Revision Notes

5 Notations — Core Definitions

O(g(n)) — Big-O f ≤ c·g for all n≥n₀. ∃ c,n₀. Upper bound. "AT MOST"
Ω(g(n)) — Big-Omega f ≥ c·g for all n≥n₀. ∃ c,n₀. Lower bound. "AT LEAST"
Θ(g(n)) — Theta c₁g ≤ f ≤ c₂g. Tight bound. "EXACTLY". O AND Ω together.
o(g(n)) — little-o f < c·g for ALL c. Strict upper. Big-O with functional gap.
ω(g(n)) — little-ω f > c·g for ALL c. Strict lower. Big-Ω with functional gap.
Key Difference Big-O/Ω: ∃ one c works. Little-o/ω: ∀ c must work.

Growth Rate Order

1 < log n < √n < n < n log n < n² < n³ < 2ⁿ < 3ⁿ < n! < nⁿ
